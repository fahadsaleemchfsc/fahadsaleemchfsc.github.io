GoHighLevel to HubSpot migration

Contacts, emails and text messages moved into HubSpot with a pipeline that could stop, resume and verify itself.

In one paragraph

A business moving back to HubSpot from GoHighLevel wanted its email and text-message history to come with it. I wrote a Python pipeline that matches contacts by email, preserves the original creation date, writes each email and text as a HubSpot engagement with the right associations, checkpoints its progress so it can stop and resume, deduplicates against the live portal, and backfills message bodies inside the daily API quota.

Background

CRM migrations usually move contacts, companies and deals. The conversation history, the emails and text messages that explain why a contact is where it is, is the part most migrations drop because it is large, rate-limited and awkward to map. This business wanted it kept.

The problem in detail

Both platforms enforce daily API quotas, and HubSpot's search endpoint has its own, lower limit that is not the same as the general one. An earlier partial run by someone else had already written engagements without their bodies, so the migration had to recognise and repair those rather than duplicate them. And the run was long enough that a laptop going to sleep could not be allowed to end it.

How the work was done

I matched contacts by email address and stored the original creation date on a custom property, because a contact created in HubSpot today should still report as a contact acquired years ago. The migration was treated as a resumable pipeline: every record written is recorded in a local SQLite checkpoint, so an interruption at any point resumes at the next unwritten record instead of starting over.

Before writing anything, I measured the real rate limits by observation rather than trusting the documentation, and gave the search endpoint its own pacing so that lookups did not exhaust the quota needed for writes.

What was delivered

A Python pipeline that writes emails and text messages as HubSpot engagements, associated to the right contact, with direction and timestamp preserved. Deduplication against the live portal so a re-run never creates a second copy. A body backfill that finds engagements written without content and fills them in within the daily quota. A watchdog process on a server, so the run survives a closed laptop and restarts itself if it stops.

Results

The history is in HubSpot with timestamps and direction intact. The run can be re-verified at any time by comparing the checkpoint with the portal. The client has a written plan for the remaining backfill, with the quota arithmetic showing how long it takes.

What this means for your team

  • Treat a migration as a resumable pipeline with a checkpoint, never as a one-shot import.
  • Measure rate limits before designing the run. Documentation describes the limit, observation shows the behaviour.
  • Preserve original timestamps on a custom property so reporting history stays true after the move.

Questions about this project

Can email and SMS history be migrated into HubSpot?

Yes. Emails and text messages can be written as engagements through the HubSpot API, associated to contacts, with their original timestamps and direction, provided the migration respects the daily quotas.

What happens if the migration stops halfway?

It resumes. Every written record is checkpointed locally, so the pipeline continues from the next unwritten record and deduplication prevents a second copy of anything already in the portal.

Why Python rather than a migration tool or a connector?

Because the job needed pacing per endpoint, repair of earlier partial writes and a verifiable checkpoint, none of which a generic connector offered. Code was the shortest reliable path.
