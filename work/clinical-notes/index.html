Background

Electronic health record (EHR) systems hold clinical notes that are signed by a provider when complete. Other systems sometimes need those signed notes, for billing, operations or compliance, and get them through the vendor's API. EHR APIs are often partially documented, and access is scoped to the provider whose notes they are.

The problem in detail

The platform team had a specification based on the documentation. The documentation did not match the API. Building against the specification would have produced an integration that failed on real accounts, and nobody could say in advance where.

How the work was done

Every relevant endpoint was exercised against a real account, with the actual responses recorded as sample payloads. Providers were mapped between the two systems and the access rules checked, since a note is only readable with the right provider context. The difference between what the platform expected and what the API delivered was written as a gap specification, with each open question assigned an owner.

What was delivered

An API capability map with sample payloads. A gap specification for the platform team. A handover document for the next developer, so the knowledge did not leave with me.

Results

The platform team could build the integration from verified behaviour rather than assumptions, and the open questions were listed with owners.

What this means for your team

  • Test the API against a real account before writing the integration. Documentation is a claim, a response is a fact.
  • Map identities between systems early. Access rules usually depend on them.
  • Write the gap down. A specification of what the API cannot do is as valuable as what it can.

Questions about this project

What is an API capability map?

A document listing each endpoint that matters, what it accepts, what it actually returns with sample payloads, and the access conditions, verified by calling it.

Why did access depend on the provider?

Clinical notes belong to the provider who signed them, and the EHR scopes API access accordingly. Reading notes requires the right provider mapping.

Did you build the final integration?

No. The engagement was discovery and specification, handed to the platform's own team with a handover document for the next developer.
