Wrong-association detection

A scheduled scan that finds contacts linked to the wrong account and queues each fix for approval.

Salesforce data-quality tooling
Platform
Salesforce, Data quality
Stack
Salesforce, Python, Tooling API, Scheduled jobs

In one paragraph

Bulk imports had linked contacts to the wrong accounts in a Salesforce org. I built a scheduled scan that compares each contact's email domain with its account, allowing for brands whose domain does not spell their name, classifies every mismatch as a confident fix, a review item or a legitimate parent-and-subsidiary case, and queues each change for a person to approve before it touches the CRM.

The challenge

Bulk imports had attached people to the wrong accounts, and nobody wanted a script rewriting records without review. The team also had a large set of active flows with no failure history to learn from.

Approach

  • Compared each contact’s email domain with the account it sits under, with an alias list for brands whose domain does not spell their name.
  • Classified every mismatch as a confident fix, a review item or a legitimate parent-and-subsidiary case.
  • Read every active flow for missing fault paths, queries inside loops and hard-coded IDs.

What was built

  • A scan that runs on a schedule and writes findings with the evidence for each one.
  • An approval step so a person confirms every change before it reaches the CRM.
  • A set of written use cases handed to the development team to build the production version.

Outcome

The client knows exactly how much of its contact base is misfiled and why, and has a reviewable path to fixing it rather than a one-off clean-up.

Background

In Salesforce, a contact belongs to an account, and most reporting, ownership and territory logic flows from that link. When an import attaches people to the wrong accounts, every downstream number is quietly wrong, and the usual fix is a script that rewrites records in bulk, which nobody with a production org wants to run blind.

The problem in detail

The team knew the data was misfiled but not how much of it, or why. They also had a large set of active flows with no failure history, which made them nervous about any automation touching records. The requirement was clear: find the problems, show the evidence, and let a person decide.

How the work was done

The scan compares the domain of each contact's email address with the account it sits under. An alias list handles brands whose web domain does not spell the company name. Each mismatch is classified: a confident fix where the correct account is unambiguous, a review item where a person should look, or a legitimate case such as a subsidiary whose people use the parent's domain.

Alongside the scan, I read every active flow for the three failure patterns that cause most production trouble: missing fault paths, queries inside loops and hard-coded record IDs. The findings went into the same report so the team could see the whole picture of their automation risk.

What was delivered

A scan that runs on a schedule and writes its findings with the evidence for each one, so a reviewer can see why a contact was flagged. An approval step so that no change reaches the CRM without a person confirming it. A set of written use cases handed to the client's development team to build the production version inside the org.

Results

The client knows exactly how much of its contact base is misfiled and why, and has a reviewable path to fixing it rather than a one-off clean-up that would need repeating after the next import.

What this means for your team

  • Never let a script rewrite production records without a person in the loop. Propose, then approve.
  • Attach evidence to every finding. A list of record IDs is not a case for change.
  • Classify mismatches. Not every mismatch is an error, and parent-and-subsidiary relationships are the usual exception.

Questions about this project

How do you detect contacts linked to the wrong account in Salesforce?

By comparing the contact's email domain with the account's known domains, with an alias list for brands whose domain differs from their name, and by classifying each mismatch before anyone acts on it.

Does the scan change records automatically?

No. It writes findings and proposed changes. A person approves each one, and only approved changes are applied.

What were the flow problems you looked for?

Missing fault paths, which hide errors; queries inside loops, which hit governor limits; and hard-coded IDs, which break between sandbox and production.
